## Task B4-T1: Verify and harden IRLSeeder env gate

| Field | Value |
|-------|-------|
| **Task ID** | B4-T1 |
| **Priority** | P1 |
| **Source Evidence** | `CRITICAL_FINDINGS_REGISTER.md` CF-06 |
| **Finding Reference** | CF-06 — IRLSeeder contains real PDPA data (900 lines), 3-layer env gate. Physically present and could be regenerated by GombakDataExtractor. |
| **Problem Statement** | `database/seeders/IRLSeeder.php` contains real trainee/centre data for Gombak centre. It is protected by: (1) `app()->environment()` check, (2) `APP_DEBUG=false` check, (3) documentation. While the env gate prevents execution outside local, it does not prevent the file from being read, copied, or accidentally committed to a branch that bypasses the gate. |
| **Affected Files** | `database/seeders/IRLSeeder.php` |
| **Affected Components** | Seeder execution, staging environment, PDPA boundary |
| **Dependencies** | Wave 1 complete (real data secured) |
| **Execution Preconditions** | [ ] `STAGING_SEED_POLICY.md` still enforced. [ ] `.env.staging` sets `APP_ENV=staging` and `APP_DEBUG=false`. |
| **Verification Steps** | 1. Read IRLSeeder.php — verify the env gate is at the TOP of the `run()` method (before any DB operations). 2. Test gate: temporarily set `APP_ENV=staging` and run `php artisan db:seed --class=IRLSeeder` — must throw RuntimeException. 3. Test gate: set `APP_ENV=local` but `APP_DEBUG=false` — must throw RuntimeException. 4. Test gate: set `APP_ENV=local` and `APP_DEBUG=true` — must execute (current expected behavior). 5. Consider adding an additional gate: check for a specific env flag `IRL_SEEDER_ENABLED=true` that is never set in any committed `.env` file. 6. Ensure IRLSeeder is NEVER included in `DatabaseSeeder.php` call chain for non-local environments. 7. Consider adding a `php artisan tinker` gate — a malicious tinker session could call `Artisan::call('db:seed', ['--class' => 'IRLSeeder'])` if APP_ENV is local. |
| **Rollback Strategy** | Adding env checks is additive — they don't break existing behavior. If a new gate accidentally blocks legitimate local use, remove the gate. |
| **Completion Criteria** | [ ] IRLSeeder cannot execute outside `APP_ENV=local` + `APP_DEBUG=true`. [ ] Additional gate considered and implemented if deemed necessary. [ ] `STAGING_SEED_POLICY.md` references updated if new gates added. |
| **Estimated Effort** | 15-30 minutes |
| **Risk of Change** | LOW — additive security check. No existing behavior changed. |
| **Notes** | The real data in IRLSeeder was used to seed the Gombak centre during development. It should never run in staging, UAT, or production. The env gate is the last line of defense — verify it is bypass-proof. |

## Task B4-T3: Strip PII from Log::debug calls in auth path

| Field | Value |
|-------|-------|
| **Task ID** | B4-T3 |
| **Priority** | P1 |
| **Source Evidence** | `CRITICAL_FINDINGS_REGISTER.md` CF-08, `DELTA_REEVAL_REPORT_2026-03-22.md` C2, `PRE_DEPLOY_SECURITY_CHECKLIST.md` item 5.3 |
| **Finding Reference** | CF-08 — Session PII logged on every authenticated request (email, IIUM ID at debug level) |
| **Problem Statement** | `MainController.php` (10+ locations), `NotificationController.php` (2 locations), and `TraineeHomeController.php` (4 locations) log `session()->all()` at debug level. This includes user email and IIUM ID. Wave 2 (B2-T2) applied `LOG_LEVEL=warning` as a quick fix. This task applies the thorough fix — strip PII from log context so debug logging can be safely re-enabled. |
| **Affected Files** | `app/Http/Controllers/MainController.php`, `app/Http/Controllers/NotificationController.php`, `app/Http/Controllers/TraineeHomeController.php` |
| **Affected Components** | Logging, PDPA compliance |
| **Dependencies** | B2-T2 (LOG_LEVEL=warning must be in place as safety net). B3-T1 (logout fix — MainController is the logout handler). |
| **Execution Preconditions** | [ ] B3-T1 complete (MainController changes tested). [ ] B2-T2 complete (LOG_LEVEL safety net active). [ ] 359 PHPUnit tests passing. |
| **Verification Steps** | 1. In each affected controller method, find `Log::debug()` calls that include `session()->all()` or individual session fields. 2. Replace `session()->all()` with an array that excludes PII: `['user_id' => session('id'), 'role' => session('role'), 'centre_id' => session('centre_id')]`. 3. Replace `Log::debug()` with `Log::info()` so these are visible at default log level. 4. If the log call was purely for debugging and has no operational value, delete it entirely. 5. After changes: trigger a login. Check `storage/logs/laravel.log` — must NOT contain email or IIUM ID. 6. Run `php artisan test` — all 359 must still pass. 7. After verification, `LOG_LEVEL` can be changed from `warning` back to `info` or `debug` (optional — keep at warning for extra safety). |
| **Rollback Strategy** | `git checkout` each controller file individually. Test login after each rollback. |
| **Completion Criteria** | [ ] 0 Log::debug() calls include `session()->all()` or individual PII fields. [ ] Login event logs user_id, role, centre_id — but NOT email or IIUM ID. [ ] All 359 PHPUnit tests passing. [ ] YELLOW item 5.3 in pre-deploy checklist → GREEN (thorough fix applied). |
| **Estimated Effort** | 30-45 minutes |
| **Risk of Change** | MEDIUM — touching 3 controllers, including the login handler (MainController). Any regression in MainController breaks authentication. Must verify login + logout + dashboard access after changes. |
| **Notes** | This is the thorough version of B2-T2. If B2-T2 (LOG_LEVEL=warning) is sufficient for immediate safety, this task can be deferred to Wave 5. The PRE_DEPLOY_SECURITY_CHECKLIST item 5.3 becomes GREEN with either approach. |

## Task B4-T4: Restrict CORS to known production origins

| Field | Value |
|-------|-------|
| **Task ID** | B4-T4 |
| **Priority** | P1 |
| **Source Evidence** | `CRITICAL_FINDINGS_REGISTER.md` CF-09, `config/cors.php` |
| **Finding Reference** | CF-09 — CORS `allowed_origins: ['*']` — overly permissive |
| **Problem Statement** | `config/cors.php` allows all origins (`*`), all methods, all headers for `api/*` and `sanctum/csrf-cookie` paths. Current auth is session-based (not API token), so practical risk is low. But if API tokens are later introduced for a mobile app, this becomes a serious vulnerability. |
| **Affected Files** | `config/cors.php` |
| **Affected Components** | CORS middleware, API security |
| **Dependencies** | None |
| **Execution Preconditions** | [ ] Know the exact production domains: pdk-creams.org, www.pdk-creams.org, creams.faisalhanafi.com (if API accessed from staging). |
| **Verification Steps** | 1. Edit `config/cors.php`: change `'allowed_origins' => ['*']` to `'allowed_origins' => ['https://pdk-creams.org', 'https://www.pdk-creams.org']`. Add staging domain if API is accessed from there: `'https://creams.faisalhanafi.com'`. 2. If local development needs wildcard CORS: use `env('CORS_ALLOWED_ORIGINS', 'https://pdk-creams.org')` and set different values per environment. 3. Test: from a different origin, attempt an API call. Should be rejected with CORS error. 4. Test: from the allowed origin, make a dashboard API call. Should succeed. 5. Run `php artisan test` — all 359 must still pass. |
| **Rollback Strategy** | Restore `'allowed_origins' => ['*']` if CORS restriction breaks legitimate cross-origin access. |
| **Completion Criteria** | [ ] `allowed_origins` restricted to known production domains. [ ] API calls from unauthorized origins rejected. [ ] API calls from authorized origins succeed. [ ] 359 PHPUnit tests passing. |
| **Estimated Effort** | 10 minutes |
| **Risk of Change** | LOW — current API usage is minimal (dashboard search, calendar data). Session-based auth means the API is only called from the same origin in normal use. |
| **Notes** | Do NOT restrict `allowed_methods` or `allowed_headers` — only restrict origins. Over-restricting methods/headers could break the dashboard AJAX calls. |
