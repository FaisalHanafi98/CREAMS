## What is the CREAMS System?

CREAMS (Community-based REhAbilitation Management System) is a comprehensive web-based management platform designed specifically for Malaysia's rehabilitation center network. Built on Laravel 10.x with PHP 8.1+, it serves as a centralized system for managing rehabilitation services, educational programs, and administrative operations across multiple rehabilitation centres.

The system implements a sophisticated centre-centric multi-tenant architecture where each rehabilitation centre operates as an independent entity while sharing the same codebase and infrastructure.

## Who are the End Users?

**Primary Users:**
- **Administrators**: System-wide management, user creation, centre oversight
- **Supervisors**: Centre-level management, activity coordination, staff supervision
- **Teachers/Instructors**: Activity delivery, session management, trainee progress tracking
- **AJK (Committee Members)**: Limited access for viewing and basic operations
- **Support Staff**: Various operational roles with restricted access

**Secondary Users:**
- **Trainees**: Individuals receiving rehabilitation services (limited direct system access)
- **Parents/Guardians**: Future integration planned for progress tracking
- **Centre Directors**: Administrative oversight and reporting

## What Problems Does It Solve?

**Administrative Challenges:**
- Manual paperwork and record-keeping across multiple centres
- Inconsistent data management and reporting standards
- Difficulty tracking trainee progress and attendance
- Complex scheduling and resource allocation
- Letter generation and official documentation processes

**Operational Challenges:**
- Activity planning and session management
- Trainee enrollment and progress monitoring
- Staff coordination and role management
- Asset and resource tracking
- Inter-centre communication and standardization

**Compliance & Quality:**
- Standardized rehabilitation protocols
- Audit trail maintenance
- Progress documentation and reporting
- Quality assurance across centres

## Role Hierarchy & Access Control

**ADMIN (Highest Level)**
- **Global Access**: All centres, all functions
- **User Management**: Create/edit/delete all user types
- **System Configuration**: Centre management, system settings
- **Activity Management**: Full CRUD operations on activities
- **Letter Generation**: Create, manage, and archive letters
- **Asset Management**: Full inventory and maintenance control
- **Reporting**: Access to all reports and analytics
- **Special Features**: System health monitoring, database operations

**SUPERVISOR (Centre-Level Management)**
- **Centre-Scoped Access**: Own centre data only
- **Staff Coordination**: Manage teachers and AJK within centre
- **Activity Oversight**: Create/edit activities, manage sessions
- **Trainee Management**: Full access to trainee records and progress
- **Letter Generation**: Create and manage centre-specific letters
- **Reporting**: Centre-specific reports and analytics
- **Resource Management**: Centre assets and scheduling

**TEACHER (Operational Level)**
- **Session Management**: Conduct sessions, mark attendance
- **Activity Access**: View and manage assigned activities
- **Trainee Interaction**: Track progress, update notes
- **Schedule Management**: View and manage personal schedule
- **Limited Creation**: Can create activities with approval workflow
- **Progress Reporting**: Submit trainee progress reports

**AJK (Committee Member - Limited Access)**
- **View-Only Access**: Activities, trainees, schedules
- **Basic Operations**: Attendance viewing, report access
- **No Creation/Editing**: Cannot modify system data
- **Centre-Scoped**: Own centre data only

## Authentication System

**Custom Session-Based Authentication** (NOT Laravel's default Auth):
- Multi-role session management via `MultipleUserGuard.php`
- IIUM ID integration for university-based authentication
- Role-based dashboard redirection
- Centre-based data isolation enforcement
- Session structure: `id`, `role`, `name`, `centre_id`, `email`, `login_time`

🏢 CENTRE MULTI-TENANCY ARCHITECTURE
===============================================================================

## Data Segregation Strategy

**Centre-Centric Design:**
- Primary key: `centre_id` (string) linked to `centres` table
- Foreign key relationships enforce data isolation
- All major entities (Users, Trainees, Activities, Assets) include `centre_id`
- Query-level filtering ensures users only access their centre's data

**Implementation Details:**
- **Model Scopes**: Automatic centre filtering in Eloquent models
- **Middleware Enforcement**: Centre access validation in controllers
- **Session Management**: Centre ID stored in user session
- **Route Protection**: Centre-based route access control

**Database Tables with Centre Isolation:**
```
users (centre_id)
trainees (centre_name/centre_id)
activities (centre_id)
assets (centre_id)
activity_sessions (via activity relationship)
activity_enrollments (via activity relationship)
```

## Cross-Centre Operations

**Limited Cross-Centre Access:**
- Admin role only for system-wide operations
- Reporting aggregation across centres
- User management and centre creation
- System maintenance and monitoring

## Data Model Architecture

**Core Entity Relationships:**
```
activities (Main Table)
├── id (PK)
├── category (ENUM) - Rehabilitation/Academic classification
├── created_by (FK → users.id) - Activity creator
├── centre_id (FK → centres.centre_id) - Centre isolation
├── duration_minutes, min/max_participants, difficulty_level
└── is_active, times_conducted, average_rating

activity_sessions (Session Instances)
├── id (PK)
├── activity_id (FK → activities.id)
├── teacher_id (FK → users.id) - Session conductor
├── scheduled_date, start_time, end_time, venue
└── status (scheduled/ongoing/completed), attendance_marked

activity_enrollments (Activity-Level Registration)
├── activity_id (FK → activities.id)
├── trainee_id (FK → trainees.id)
├── enrolled_by (FK → users.id)
├── enrollment_date, status, progress_notes
└── attendance_rate, sessions_attended

session_enrollments (Session-Level Tracking)
├── session_id (FK → activity_sessions.id)
├── trainee_id (FK → trainees.id)
├── attendance_status (present/absent/late/excused)
└── participation_score, progress_notes, checked_in_at
```

## Workflow: Creation → Delivery → Tracking

**Phase 1: Activity Creation**
1. Admin/Supervisor creates base activity with category and details
2. Activity assigned to primary creator/coordinator
3. Equipment and material requirements specified
4. Age group and difficulty level set

**Phase 2: Session Scheduling**
1. Sessions created with specific dates and times
2. Teachers assigned to individual sessions
3. Venue and capacity requirements set
4. Recurring schedule patterns supported

**Phase 3: Trainee Enrollment**
1. Trainees enrolled in activities (not specific sessions)
2. Individual goals and objectives set
3. Progress tracking baseline established
4. Session-specific enrollment generated

**Phase 4: Session Delivery**
1. Teachers mark attendance per session
2. Participation scores recorded (0-10 scale)
3. Progress notes captured
4. Session status updated (scheduled → ongoing → completed)

**Phase 5: Progress Tracking**
1. Attendance rates calculated automatically
2. Participation trends tracked
3. Goal achievement measured
4. Reports generated for stakeholders

## Category System Implementation
